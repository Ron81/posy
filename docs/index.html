Avatar poses in 115 bytes a frame

Posy streams a whole room of avatars — body, fingers, face — in real time, in about 115 bytes a frame. WebRTC data channel or WebSocket, open spec, nothing to sign up for.

Is it for you?

A fit

  • You're building something where lots of avatars move together
  • Bandwidth and the odd dropped frame are things you have to care about
  • You want body, fingers and face — plus room for extras — on VRM 1.0, VRM 0.x and PMX
  • You want the motion online fast, not perfect

Probably not

  • You want a lossless mocap recording — grab VMC or BVH instead
  • It never leaves your home network (works fine, just not much point)

How it works

This page is the pitch. The exact rules — coordinate space, packet layout, who's allowed to send what — live in spec/Posy.md.

Every frame goes from the sender to the server, and the server hands it to everyone else. The server sets the tempo, keeps the clock and decides who may send what. It barely breaks a sweat doing it, so a spare PC or a cheap VPS is plenty.

  1. The sender declares, then sends. It says up front which data types its tracker produces and its avatar can show, and sends only those. A lost frame is just gone — nothing is ever resent.
  2. The server forwards — as long as it adds up. It checks that a frame's length matches what the sender was granted, and never reads the rotations themselves. Slip it something that doesn't fit and it bins the whole frame, untouched.
  3. The receiver does the rest. Each receiver takes the frame, drives its copy of the sender's avatar, smooths between frames and papers over short gaps. Nobody's motion gets retargeted onto someone else's rig.
Posy avatar space (§3)
It's the normalized VRM 1.0 rig, as-is — no new wheel invented. VRM 0.x and PMX avatars get adapted on each end (§3.2); the wire is identical for all three.
Everything past the humanoid (§2.6)
Cat ears, wings, tails, extra limbs, an avatar's own expressions: all optional, declared extras — whatever the avatar file brings. The sender names them once; no names travel on the wire, just the data.

Bandwidth

Each tracked user uploads one stream, and that stays the same whether two people are watching or two hundred. So as a sender you don't care how big the room gets — unless you're the one hosting the server. The server has to send everything to everyone, and that's where the bytes pile up.

Tables of the spec

The handful of tables you actually look up while building. The full, normative text is spec/Posy.md.

A 64-bit mask. Bit n set means the quaternion of bone n is present; quaternions follow in ascending bit order. The colours are the declared types a bit belongs to. The server refuses a frame that sets a bit of a type the sender was not granted, or one of bits 55–63.

One byte per slot, 0–255 for 0.0–1.0. Both blocks end with two i8 gaze bytes, yaw and pitch, ±127 for ±45°: the line of sight, measured from the head. The Perfect-Sync order is the 52 ARKit names sorted by code unit. A tongue, and any expression beyond these, is a declared extra value.

24 bytes: left hand (12 B), then right hand (12 B). Per hand:

offsettypefield

Curl (0 = straight … 255 = fully curled) bends all three joints of a finger: proximal 90°, intermediate 110°, distal 70°, about Z, into the palm.

Splay (−127…+127 for −30°…+30°) turns the proximal joint about Y; positive is toward the thumb side.

The thumb is driven by its three bytes together: splay ±90° in the palm's plane, opposition 0–60° toward the palm with an equal roll, curl 60° and 80° on the two outer joints. A receiver measures once how its avatar's thumb rests and turns the result accordingly. The definition is in spec §5.5; the pose vectors f01–f09 pin it.

A frame carries this block or per-joint finger bones (bits 25–54), never both. With neither, a receiver shows the rest hand.

Errors are enforced by the server. A receiver checks a frame's length and nothing else: it only sees frames the server has let through.

Implementing Posy

  1. Read the spec and build it. §3 (avatar space), §4 (bones) and §5 (packets) of spec/Posy.md are where every implementation has to agree. §2 is the session layer. Honestly, you can stop there — the rest is nice-to-have.
  2. Grab the reference codec. posy-protocol on npm (reference/js): TypeScript, zero runtime dependencies. It's a leg-up, not a requirement.
  3. Run it against the test vectors. testvectors/frames checks the bytes — every .bin against its .json. testvectors/poses mostly catches anything you accidentally flipped.
  4. Watch it move. The loopback demo runs an avatar through a deliberately lossy channel — i.e. real, crap internet — right in the browser, no server.
npm install posy-protocol
