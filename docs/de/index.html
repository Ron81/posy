Avatar-Bewegungen mit nur 115 Bytes pro Frame

Posy ist ein offenes Protokoll, das Körper-, Finger- und Gesichtsbewegungen von Avataren in Echtzeit zwischen mehreren Teilnehmern über einen WebRTC-Datenkanal oder einen WebSocket übertragen kann.

Spec lesen Demo öffnen Frame bauen Apache-2.0 · Kanal-Label avatar-pose · Protokoll posy/1 · Spec und Demo sind nur auf Englisch

1

Ist es was für deine App?

Optimal, wenn

  • Avatarbewegungen vieler Nutzer übertragen werden
  • Bandbreite und Fehlertoleranz ein Thema sind
  • Neben Fullbody & Face weitere Extras benötigt werden
  • Bewegungsdaten schnell online übertragen werden sollen

Eher nichts, wenn

  • Motion-Capture verlustfrei aufgezeichnet werden soll (nimm VMC)
  • Das Ganze eh nur im Heimnetzwerk bleibt (geht, bringt aber wenig)
2

Funktionsweise

Jeder Bewegungs-Frame geht vom Sender zum Server und von dort zu den Empfängern. Der Server gibt Takt, Uhrzeit und Berechtigungen vor. Er braucht kaum Power, kann also locker auch auf einem lokalen PC oder einem kleinen gehosteten VPS laufen.

  1. Der Sender deklariert, dann sendet er. Er deklariert die Datentypen, die sein Tracker liefert und sein Avatar zeigen kann, und sendet nur diese. Ein verlorener Frame ist weg und wird nicht neu gesendet.
  2. Der Server serviert. Zumindest solange die Länge der Frames dem entspricht, was dem Sender gewährt wurde. Wird ihm was Falsches untergeschoben, verwirft er den ganzen Frame, ohne die Rotationen überhaupt anzufassen.
  3. Der Empfänger rendert den ganzen Bumms. Jeder Empfänger verwendet die Daten der Frames, um die Avatarbewegungen darzustellen, interpoliert zwischen den Frames und überbrückt kurze Lücken.

Bandbreite

Jeder User mit Tracking lädt jeweils einen Stream hoch und der Server schickt ihn an alle Teilnehmer. Dem User kann es also egal sein, wie viele Leute dabei sind, solange er nicht selbst den Server hostet. Der Server hingegen muss alles an alle weiterleiten, da kann sich die Bandbreite schnell summieren.

Tabellen der Spec

Der vollständige und normative Text ist spec/Posy.md, auf Englisch.

Eine 64-Bit-Maske. Ist Bit n gesetzt, ist das Quaternion von Knochen n vorhanden; die Quaternionen folgen in aufsteigender Bit-Reihenfolge. Die Farben zeigen den deklarierten Typ, zu dem ein Bit gehört. Setzt ein Frame ein Bit, dessen Typ dem Sender nicht gewährt wurde, oder eines der Bits 55–63, lehnt der Server ihn ab.

Ein Byte pro Slot, 0–255 für 0,0–1,0. Beide Blöcke enden mit zwei i8-Blick-Bytes, Yaw und Pitch, ±127 für ±45°: die Blickrichtung, vom Kopf aus gemessen. Die Perfect-Sync-Reihenfolge sind die 52 ARKit-Namen, nach Code-Unit sortiert. Eine Zunge und jedes Emote darüber hinaus ist ein deklarierter Extra-Wert.

24 Bytes: linke Hand (12 B), dann rechte Hand (12 B). Pro Hand:

OffsetTypFeld

Curl (0 = gestreckt … 255 = ganz gebeugt) beugt alle drei Gelenke eines Fingers: Grundgelenk 90°, Mittelgelenk 110°, Endgelenk 70°, um Z, zur Handfläche hin.

Splay (−127…+127 für −30°…+30°) dreht das Grundgelenk um Y; positiv heißt: zur Daumenseite.

Der Daumen wird von seinen drei Bytes gemeinsam gesteuert: Splay ±90° in der Ebene der Handfläche, Opposition 0–60° zur Handfläche hin mit einer gleich großen Rollbewegung, Curl 60° und 80° an den beiden äußeren Gelenken. Ein Empfänger misst einmal, wie der Daumen seines Avatars in Ruhe steht, und dreht das Ergebnis entsprechend. Die Definition steht in Spec §5.5; die Pose-Vektoren f01–f09 legen sie fest.

Ein Frame enthält diesen Block oder Fingerknochen pro Gelenk (Bits 25–54), nie beides. Ohne beides zeigt ein Empfänger die Ruhehand.

Um Fehler kümmert sich der Server. Ein Empfänger prüft die Länge eines Frames und sonst nichts: er sieht nur Frames, die der Server durchgelassen hat.

Posy implementieren

  1. Die Spec lesen und implementieren. §3 (Avatar-Raum), §4 (Knochen) und §5 (Pakete) von spec/Posy.md sind das, wo jede Implementierung übereinstimmen muss. §2 beschreibt den Session Layer. Hier kannst du eigentlich schon aufhören, der Rest ist nice to have.
  2. Referenz-Codec nutzen. Das posy-protocol auf npm (reference/js) ist in TypeScript geschrieben, hat keine Laufzeit-Abhängigkeiten und ist per se nur eine Implementierungshilfe.
  3. Teste deine Implementierung mit den testvectors/frames. Sie prüfen Bytes: jede .bin wird mit ihrer .json verglichen. testvectors/poses checkt hauptsächlich, ob irgendwas aus Versehen invertiert wurde.
  4. Schau dir die Loopback-Demo an. Sie simuliert einen verlustbehafteten Kanal, ergo scheiß Internet.
npm install posy-protocol
